# QR/referral API для frontend

## Назначение и сценарий

Каждый автосервис может один раз создать постоянный публичный код. Из него
формируются две ссылки: регистрация с неизменяемой атрибуцией и гостевая запись
без регистрации. Код не раскрывает внутренний ID организации и не даёт доступ
к административным данным.

Обычный сценарий:

1. Администратор автосервиса создаёт ссылку и получает QR.
2. Ссылку публикуют в соцсетях или печатают QR.
3. Клиент открывает ссылку вида `https://app.example.ru/r/AbCdEf0123_-XyZ9`.
4. Web/mobile-клиент извлекает код из пути и сохраняет его до подтверждения OTP.
5. При подтверждении OTP frontend передаёт код в `referral_code`.
6. Backend навсегда фиксирует организацию-источник, если у клиента источника ещё
   нет. Повторные переходы и сканирования его не меняют.

Все API-пути ниже имеют префикс `/api/v1`.

## Административный API

Для всех endpoint'ов раздела нужен staff access token пользователя с ролью
`admin`:

```http
Authorization: Bearer <staff_access_token>
```

### Создать или получить ссылку

`POST /api/v1/referrals/me`

Создаёт постоянный код для организации текущего администратора. Первый запрос
возвращает `201 Created`, повторные запросы возвращают тот же код и
`200 OK`.

Тело запроса отсутствует.

```json
{
  "code": "AbCdEf0123_-XyZ9",
  "url": "https://app.example.ru/client/r/AbCdEf0123_-XyZ9",
  "qr_svg": "<?xml version='1.0' encoding='UTF-8'?><svg ...>...</svg>",
  "booking_url": "https://app.example.ru/client/book/AbCdEf0123_-XyZ9",
  "booking_qr_svg": "<?xml version='1.0' encoding='UTF-8'?><svg ...>...</svg>"
}
```

`url`/`qr_svg` относятся к регистрации и сохраняются для обратной
совместимости. Для размещения на картах и создания заявки без аккаунта frontend
должен использовать `booking_url`/`booking_qr_svg`.

### Получить существующую ссылку

`GET /api/v1/referrals/me`

Возвращает тот же JSON, что и `POST`. Если ссылка ещё не создавалась:

```json
{
  "detail": "Реферальная ссылка ещё не создана"
}
```

Статус — `404 Not Found`.

### Скачать QR как SVG

`GET /api/v1/referrals/me/qr.svg`

Возвращает SVG-файл с `Content-Type: image/svg+xml` и
`Content-Disposition: inline; filename="referral-qr.svg"`. QR кодирует ровно
значение поля `url`. Формат векторный и подходит для печати; frontend может
открыть endpoint в новой вкладке, скачать ответ как `Blob` или использовать
поле `qr_svg` из JSON для предпросмотра.

### Скачать QR гостевой записи как SVG

`GET /api/v1/referrals/me/booking-qr.svg`

Возвращает `booking_qr_svg` как файл `public-booking-qr.svg`. QR кодирует ровно
`booking_url`; регистрационные токены, staff-токены и внутренний ID организации
в него не входят.

Типовые ошибки административных endpoint'ов:

- `401` — access token отсутствует, неверен или истёк;
- `403` — пользователь авторизован, но не является администратором;
- `404` — ссылка ещё не создана (`GET` и `qr.svg`).

## Клиентский OTP API

### Запросить OTP

`POST /api/v1/client-auth/otp/request`

Авторизация не нужна. Реферальный код сюда передавать не требуется.

```json
{
  "phone": "+79990001122"
}
```

Ответ:

```json
{
  "detail": "Код отправлен",
  "debug_code": null
}
```

`debug_code` заполняется только в debug-окружении.

### Подтвердить OTP и применить код

`POST /api/v1/client-auth/otp/verify`

Авторизация не нужна. `referral_code` опционален, поэтому старые клиенты API
могут продолжать отправлять только телефон и OTP.

```json
{
  "phone": "+79990001122",
  "code": "4821",
  "referral_code": "AbCdEf0123_-XyZ9"
}
```

Успешный ответ:

```json
{
  "access_token": "<client_access_token>",
  "refresh_token": "<client_refresh_token>",
  "token_type": "bearer"
}
```

Точная логика:

- новый клиент + действительный код: аккаунт создаётся и получает этот
  неизменяемый источник;
- новый клиент без кода: аккаунт создаётся без источника;
- существующий клиент без источника + действительный код: источник фиксируется;
- существующий клиент с источником + любой новый код: вход проходит, ранее
  сохранённый источник не меняется;
- клиент без источника + неизвестный код: `422` с сообщением
  `Недействительный реферальный код`;
- неверный или истёкший OTP: `401` с сообщением
  `Неверный или истёкший код`.

Не следует показывать реферальный код как пароль или секрет: это публичный
идентификатор кампании.

## Настройка ссылки и deep link

Backend формирует ссылки из переменной окружения `PUBLIC_CLIENT_BASE_URL`.
Она должна указывать на корень клиентского SPA. Например, при значении
`https://app.example.ru/client` ссылки имеют вид
`https://app.example.ru/client/r/<code>` и
`https://app.example.ru/client/book/<code>`. Значение должно быть публичным
HTTPS URL без завершающего `/`.

Frontend должен:

1. иметь маршрут `/r/:referralCode`;
2. сохранить `referralCode` до успешного OTP-входа (например, в защищённом
   локальном состоянии приложения);
3. передать сохранённое значение в `referral_code` при вызове `otp/verify`;
4. удалить локально сохранённый код после успешного ответа;
5. для mobile настроить этот HTTPS-домен как Universal Link / Android App Link,
   а web fallback направить на экран входа.

QR не требует отдельного сканирующего API: системная камера открывает ту же
HTTPS-ссылку, что используется в соцсетях.
